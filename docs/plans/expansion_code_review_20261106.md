## Runtime and memory

Measured the actual 3.0 pit reference table through the regional pooled-bootstrap helper: 115 blocks, 778 candidates, 30 replicates in **1.309 s** on this host. Linear extrapolation is about **87 s for 2,000 replicates**, excluding additional interval/permutation passes and startup. This is a measured scaling concern, not a demonstrated runtime failure. The helper copies/concatenates candidate DataFrames and sorts for each draw; counts-only resampling is cheaper only if the statistical estimand permits fixing the selected candidate set.

Static memory bound: [expansions/5_tasks/5_6_record_association/src/_records_assoc_core.py:156](C:/Users/colto/Documents/GitHub/lidar_project/expansions/5_tasks/5_6_record_association/src/_records_assoc_core.py:156) materializes dense distance and cost arrays for Hungarian assignment. At 100,000 records × 10,000 detections, each float64 matrix is 8 GB, and D+C alone require 16 GB, with broadcast temporaries beyond that. No allocation at that scale was attempted. A spatial gate followed by sparse connected-component assignment would bound this cost. The existing 9t row counts do not themselves demonstrate an out-of-memory failure.

Regional raster extraction materializes whole arrays and connected-component labels; memory grows with raster pixels, not merely candidate count. A 10 km square at 0.5 m has 400 million pixels: a single float32/int32 plane is 1.6 GB. Several simultaneous planes exceed that by multiples. No county-sized benchmark was run. This concern should be measured on a representative pilot before a county runtime commitment.
